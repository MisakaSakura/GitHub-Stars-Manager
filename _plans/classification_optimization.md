# 分类系统优化计划

> 创建时间: 2026-05-14
> 背景: 当前"规则+LLM"双层分类存在系统性瓶颈——LLM 仅凭项目名+短描述推断，信息不足且无反馈闭环。以下按收益/工作量排序列出优化方向。

---

## P1 预分类增强（收益最大 ⭐⭐⭐，工作量中-大）

### 目标
调用 LLM 前，先用 topics + README 前 500 字做一轮**语义预分类**，把结果（platform/type/ecology 推断）写入 LLM prompt 作为参考，让 LLM 在此基础上修正而非从零推断。

### 为什么收益最大
当前 LLM 对很多项目"凭空猜测"（如 OBS 插件只看到 "plugin"+"video" 就猜游戏）。如果 prompt 中给出 `"参考分类：ecology=OBS Studio, platform=桌面端"`，LLM 的准确率会大幅提升。

### 需要修改的文件

| 文件 | 改动内容 | 预估行数 |
|------|----------|----------|
| `config_rules.py` | 新增 `PRECLASSIFY_RULES`：topics 关键词 → (platform, type, ecology) 映射 | 60-80 |
| `engine.py` | 新增 `_pre_classify(item)` 方法；`_process_single()` 中 LLM 调用前执行 | 80-120 |
| `llm_classifier.py` | `_build_prompt()` / `_build_batch_prompt()` 注入参考分类 | 30-50 |
| `tests/test_engine.py` | 预分类逻辑单元测试 | 30-50 |

### 工作量
**2.5-3.5 小时**

### 风险
- batch prompt 变长 → token 消耗增加约 10-20%
- 预分类错误可能误导 LLM（需加 `"仅供参考，如有不符请修正"` 说明）

---

## P2 人工反馈闭环（长期价值 ⭐⭐⭐，工作量最大）

### 目标
在报告页面每个项目行增加"纠错"按钮，用户点击后记录 `{repo, wrong, correct}` 到 `classification_feedback.json`。下次运行时优先用反馈覆盖 LLM 结果，并批量修正相同 patterns 的项目。

### 为什么工作量大
GitHub Pages 是**纯静态页面**，没有后端存储。需要解决数据持久化问题：
- 方案 A：localStorage 存储 → 用户手动导出 JSON → 放入仓库（最可行）
- 方案 B：GitHub Issues API（需要 token，复杂）
- 方案 C：生成 JSON 下载链接（用户下载后手动上传）

前端交互（弹窗、下拉、 localStorage、导出）开发耗时。

### 需要修改的文件

| 文件 | 改动内容 | 预估行数 |
|------|----------|----------|
| `report_template.html` | 每行增加纠错按钮 + 弹窗选择正确分类 + localStorage 存储 + 导出 JSON | 100-150 |
| `report.py` | 生成带纠错按钮的 HTML | 20-30 |
| `feedback_manager.py` (新增) | 读取/合并/匹配反馈数据 | 80-100 |
| `engine.py` | `process()` 开头加载反馈，命中时跳过 LLM | 30-40 |
| `tests/` | 反馈匹配逻辑测试 | 40-60 |

### 工作量
**3-4 小时**

### 风险
- 用户体验一般（需要手动导出/上传 JSON）
- 前端代码量增加显著

---

## P3 分类一致性自检（中等收益 ⭐⭐，工作量中）

### 目标
增加逻辑一致性检查，自动标记可疑分类。例如：
- ecology=OBS Studio 但 platform=游戏/图形 → suspicious
- type=框架 但 stars<50 且 language 数量>3 → suspicious（可能是工具误标）

### 需要修改的文件

| 文件 | 改动内容 | 预估行数 |
|------|----------|----------|
| `engine.py` | 新增 `_check_consistency(target, llm_result)` 方法 | 60-80 |
| `ai_database.py` | 支持 `llm_status="suspicious"` | 10-20 |
| `report.py` | 可疑项目行显示 ⚠️ 标记 | 20-30 |
| `tests/` | 一致性规则测试 | 30-40 |

### 工作量
**1.5-2 小时**

### 风险
- 一致性规则需要大量调参，初期可能误报过多

---

## P4 生态自动发现（低收益 ⭐，工作量小）

### 目标
每次分类后扫描数据库，自动发现高频但未归一化的 ecology 值，输出到日志/报告。

```python
# 伪代码
for eco, count in stats["ecology"].most_common():
    if eco not in ECOLOGY_ALIASES and count >= 3:
        log(f"发现潜在新生态: {eco} ({count} 个项目)", "WARN")
```

### 需要修改的文件

| 文件 | 改动内容 | 预估行数 |
|------|----------|----------|
| `engine.py` | `process()` 结束后增加扫描逻辑 | 30-40 |

### 工作量
**20-30 分钟**

### 风险
- 几乎无风险

## 推荐实施策略

### 方案 A：一次性全部做完（1 个工作日）
适合时间充裕，想彻底解决分类问题的场景。

### 方案 B：分两次迭代（推荐）
**第一批（3-4h，半天）**：P4 + P1
- P4（0.5h）零风险热身
- P1（2.5-3.5h）核心优化，做完立刻看到分类准确率提升

**第二批（4.5-6h）**：P3 + P2
- P3（1.5-2h）在第一批运行一段时间后积累可疑样本
- P2（3-4h）长期闭环，用户可以直接在页面纠错

### 方案 C：只挑一个（最小可行）
只做 **P1 预分类增强**（2.5-3.5h），这是性价比最高的单项优化。
